# 01 · 스프링-댐퍼 기초

> 코드: [`jiggle/jiggle_spring.gd`](../jiggle/jiggle_spring.gd),
> [`demos/01_spring_basics/spring_basics_demo.gd`](../demos/01_spring_basics/spring_basics_demo.gd)

## 한 줄 요약

```
a = k · (목표 − 현재) − c · 속도
```

Jiggle의 전부다. 나머지는 이 식을 어디에 붙이고 결과를 어떻게 읽느냐의 문제일 뿐이다.

- **k (stiffness, 강성)** — 목표에서 벗어난 만큼 잡아당기는 힘. 크면 단단하다.
- **c (damping, 감쇠)** — 속도에 반대로 작용하는 저항. 크면 빨리 멈춘다.

## 왜 k와 c를 직접 만지면 안 되는가

k = 250, c = 12 라는 숫자를 보고 "얼마나 출렁일지" 감이 오는 사람은 없다.
게다가 k를 4배로 키우면 같은 c로도 훨씬 덜 출렁이게 되어 두 값이 서로 얽힌다.

그래서 이 프로젝트는 **주파수와 감쇠비**로만 파라미터를 노출한다.

```
ω = 2π · f          (f = 초당 진동 횟수, Hz)
k = ω²
c = 2 · ζ · ω       (ζ = 감쇠비)
```

`JiggleSpring.params_from_frequency(f, ζ)` 가 이 변환을 한다.
이제 두 값은 서로 독립이다. **f는 "얼마나 빠르게", ζ는 "얼마나 출렁이며"** 를 따로 조절한다.

## 감쇠비 ζ 하나가 모든 것을 결정한다

```
ζ = c / (2√k)
```

| ζ | 이름 | 거동 | 쓰는 곳 |
| --- | --- | --- | --- |
| < 1 | 부족감쇠 | 지나쳤다 되돌아오며 여러 번 출렁인다 | **거의 모든 Jiggle** (0.1 ~ 0.3) |
| = 1 | 임계감쇠 | 오버슈트 없이 가장 빠르게 도착 | 카메라 추적, UI 애니메이션 |
| > 1 | 과감쇠 | 느릿느릿 스며들 듯 도착 | 무거운 물체, 관성 큰 카메라 |

데모의 공 세 개는 **완전히 같은 목표를 쫓지만 ζ만 다르다.**
자극을 `임펄스(Space)`로 주고 그래프를 보면 세 곡선의 차이가 한눈에 들어온다.

## 적분 방식 — 같은 식, 다른 결과

미분방정식을 컴퓨터로 풀려면 시간을 잘게 쪼개야 한다. 어떻게 쪼개느냐에 따라
**같은 k, c로도 결과가 완전히 달라진다.**

### 1. 명시적 오일러 — 쓰면 안 된다

```gdscript
var accel := -x * k - v * c
x += v * delta       # 옛 속도로 위치를 옮기고
v += accel * delta   # 그 다음에 속도를 갱신
```

위치를 갱신할 때 쓰는 속도가 이미 낡은 값이라 매 스텝 에너지가 **조금씩 늘어난다.**
`k`가 크거나 `delta`가 크면 진폭이 계속 커져서 결국 발산한다.

> 데모에서 **프리셋 "발산시키기"** 를 눌러 보면 공이 화면 밖으로 날아간다.
> 이건 버그가 아니라 이 적분기의 본질이다.

### 2. 반암시적(심플렉틱) 오일러 — 실무 표준

```gdscript
var accel := -x * k - v * c
v += accel * delta   # 속도를 먼저 갱신하고
x += v * delta       # 그 새 속도로 위치를 옮긴다
```

두 줄의 **순서만** 바꿨는데 에너지가 보존되는 쪽으로 기울어 훨씬 안정적이다.
게임에서 쓰이는 스프링은 사실상 전부 이것이다. 이 프로젝트의 기본값이기도 하다.

### 3. 해석적 감쇠 스프링 — 절대 발산하지 않는다

미분방정식의 닫힌 해를 그대로 평가한다. ζ 값에 따라 세 갈래로 나뉜다.

```
ζ < 1 :  x(t) = e^(−ζωt) · (A·cos(ω_d·t) + B·sin(ω_d·t)),   ω_d = ω√(1−ζ²)
ζ = 1 :  x(t) = (A + B·t) · e^(−ωt)
ζ > 1 :  x(t) = A·e^(z₁t) + B·e^(z₂t),   z = −ζω ± ω√(ζ²−1)
```

`delta`를 아무리 키워도 발산하지 않고, **프레임레이트가 바뀌어도 결과가 완전히 같다.**
대신 축마다 따로 풀어야 하고 `exp`/`sin`/`cos` 호출이 들어가 비싸며,
충돌 같은 비선형 요소를 섞기 어렵다.

> 데모에서 **적분 방식을 '해석적 해'로 두고 Hz를 15까지 내려 보라.**
> 명시적 오일러가 터지던 조건에서도 아무 일도 일어나지 않는다.

## 프레임레이트 의존성 — 가장 흔한 버그

60fps에서 예쁘게 튜닝한 흔들림이 144Hz 모니터에서 전혀 다르게 보이는 일은
Jiggle 구현에서 가장 자주 겪는 사고다. 원인은 매 프레임 `delta`가 달라지기 때문이다.

해결책은 두 가지뿐이다.

1. **고정 timestep 서브스텝** — 프레임 delta를 1/120초 같은 고정 크기로 쪼개 여러 번 돈다.
   ([`common/jiggle_demo.gd`](../common/jiggle_demo.gd) 의 `_advance()`)
2. **해석적 해를 쓴다** — delta에 무관하므로 애초에 문제가 없다.

서브스텝에는 반드시 **상한**이 있어야 한다. 없으면 프레임이 밀릴수록 더 많이 계산해서
더 밀리는 악순환(spiral of death)에 빠진다.

```gdscript
while _accumulator >= step and steps < MAX_SUBSTEPS:
    _simulate(step)
    _accumulator -= step
    steps += 1
if steps >= MAX_SUBSTEPS:
    _accumulator = 0.0    # 따라잡기를 포기한다
```

## 중력은 힘이 아니라 평형점의 이동이다

```
a = k(목표 − x) + g  ==  k((목표 + g/k) − x)
```

상수 가속도 `g`는 **평형점을 `g/k` 만큼 옮기는 것과 수학적으로 완전히 같다.**
그래서 `JiggleSpring`은 중력을 별도 항으로 두지 않고 목표점을 옮겨 버린다.

이 사실은 실용적으로도 중요하다. 데모 02에서 가슴이 정지 상태에서도 rest보다
살짝 아래에 머무는 자연스러움은 전부 여기서 나온다. 그리고 **강성이 클수록 덜 처진다** —
`g/k`가 작아지니까. 물리적으로도 맞고 보기에도 맞다.

## 안전장치

스프링은 조건만 맞으면 언제든 폭주한다. 실무에서는 반드시 상한을 건다.

```gdscript
if max_distance > 0.0:
    _clamp_within(target, max_distance)
```

클램프할 때 **위치만 자르고 속도를 그대로 두면 안 된다.** 경계를 계속 밀어내는
속도 성분이 남아 벽에 붙어 떠는 현상이 생긴다.

```gdscript
var outward := velocity.dot(normal)
if outward > 0.0:
    velocity -= normal * outward   # 바깥으로 나가려는 성분만 제거
```

## 해볼 것

1. 자극을 **임펄스**로 두고 그래프에서 세 곡선을 비교한다. 오버슈트가 곧 "출렁임"이다.
2. **적분 방식 = 명시적 오일러, Hz = 15** → 발산을 직접 본다.
3. 같은 조건에서 **해석적 해**로 바꾼다 → 멀쩡하다.
4. **중력**을 켠다 → 정지 위치가 목표보다 아래로 내려간다. 그 상태에서 진동수를 올리면
   처짐이 줄어든다 (`g/k`).
5. **최대 이탈 거리**를 0.1로 두고 자극 세기를 키운다 → 붉은 구가 감옥이 된다.
